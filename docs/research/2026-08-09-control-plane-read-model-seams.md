## 1. Executive recommendation

The smallest deep seam over existing modules is a three-way distinction, not a layer stack:

1. **Canonical authorities** — the durable stores each module already owns and writes (SQLite DBs, build/state files, OCR metadata, JSONL, vault files — *any* format the module chooses; user-visibility is a per-module decision, **not** a seam requirement). Local-first holds: the local copy is the primary copy [S7]; git itself is "fundamentally a content-addressable filesystem" whose `.git` internals are not user-facing [S8].
2. **Derived read models** — anything recomputable from authorities (summaries, indices, status, Bases). "A materialized view is just a cached subset of the log, and you could rebuild it from the log at any time." [S18]. Read models are the client surface; raw authorities are internal (exposing them via debug/export commands is an optional per-module choice, never a contract). Freshness machinery (as_of/provenance/refresh) is required **only** for cached or externally sourced views — views freshly recomputed from local authorities are fresh by construction [S18][S9].
3. **A thin control plane** — orchestrates per invocation: command dispatch, deterministic full-probe fan-out, one-pass aggregation, partial-failure composition, exit codes. It owns **no** per-capability business logic (pass-through/anemic-service trap [S2][S3]; shallow-module trap [S17]).

CLI/Obsidian/Agent are three adapters onto the same inner API [S4][S5][S21][S22].

### Decision criteria (for the grilling ticket, applied after the local audit)
1. **Rebuildability** — a read model is acceptable only if it can be rebuilt from a module's authority; if it cannot, it is a new authority and needs the same rigor as one. [S18]
2. **Depth over uniformity** — every seam module has a small interface relative to the work it does [S17]; **no uniform status/refresh/diagnose protocol is imposed** — a module exposes only the minimal interface its commands actually need. Forcing unused methods creates shallow wrappers (reject).
3. **Dependency rule, scoped** — inner capability logic never names outer entities (TTY, Obsidian, Agent protocols, CLI libraries); **CLI command/parse modules MAY import argparse/click — they are part of the adapter** — inner capability logic may not. [S5]
4. **Deterministic full probes, one pass per invocation** — each module is probed once per command run and the aggregate is computed once within that single invocation/response; separate client invocations (CLI, Agent, Obsidian) probe independently — there is no daemon, so no cross-invocation/cross-client sharing of aggregates is implied. No sampling machinery. [S10][S23][S11]
5. **Staleness honesty where it matters** — provenance/as_of/refresh are required **only for cached or externally sourced read models**; views freshly recomputed from local authorities need no freshness machinery. [S9][S18][S16]
6. **Partial-failure contract** — a failing module degrades the report, never aborts the command; per-module outcome + aggregated tiered exit code. Per-probe timeouts are **not** required for local/deterministic probes — only where the local audit finds an actual blocking or remote probe. [S6][S19][S23]
7. **Human-first, machine-additive output** — human summary by default; `--json` opt-in, versioned, additive. [S6] + CliProtocolResearch pass (pip installation-report `version` field; gh `--json` field lists).
8. **CQRS rejected as a pattern** — only the "derive once, expose views" nugget survives Fowler's caution [S1].

## 2. Findings by decision area (evidence)

**DA-1 — Capability modules vs one aggregate control plane vs command-as-domain.** Mature local CLIs use a thin dispatcher + capability modules + shared core logic. Homebrew: one file per command in `Library/Homebrew/cmd/` [S24], external commands are separate programs [S25], shared logic accumulates in shared classes (e.g. `Diagnostic::Checks`) [S23]. hledger: journal engine is the core; "Most of these commands do not change the journal file; they just read it and output a report"; add-on commands are separate executables [S10]. git: plumbing/porcelain is a two-level seam (facts / user layer), not N peer modules [S8]. Command-as-domain applies at the dispatcher seam: Cobra "Commands represent actions" [S26]; Clean Architecture keeps use cases central [S5]. **[REC]** Commands are thin intents; capability modules hold logic; the control plane sequences and aggregates. **[INFERENCE]** An aggregate god-module is the failure mode — a shallow Service Layer; the control plane stays small precisely because everything else is deep [S17][S3].

**DA-2 — Read models over distributed canonical authorities.** Canonical authorities may be files, SQLite, or state stores — module-owned and format-agnostic. git: objects + index + config are internal `.git` state; `status`/`diff` are derived read models; plumbing exists for tooling but the raw object formats are not a user contract [S8][S9]. Kleppmann: indexes/caches/materialized views are "derived data... derived from an underlying, primary dataset, via a transformation process"; read/write separation is "really the key idea" [S18]. Local-first: local disk copy is primary [S7]. Fowler CQRS: separate read models are valuable in specific bounded contexts; "you should be very cautious about using CQRS" — full CQRS (separate processes/event store) rejected [S1]. **[REC]** Per module: authority + derived read models, each rebuildable. Freshly recomputed views carry no freshness metadata; cached or externally sourced views carry provenance and "as of" (see DA-4). Clients get read models and command results, not raw authorities. **[INFERENCE]** The client surface (read models) must be stable/versioned; authority formats are internal and free to evolve within a module — which is exactly why the read-model seam matters: it insulates consumers from authority changes.

**DA-3 — Deterministic full probes; one-pass aggregation per invocation; sampling rejected.** For local CLIs the evidence says: probe everything, deterministically, every run. hledger recomputes reports from the journal on every invocation [S10]; brew doctor runs every check, collects all findings, then exits non-zero if any problem was found [S23]; git `status` validates the working tree per run (using the index as a stat cache, not a sampling scheme) [S9]. The server-scale texts explain *why* that is possible locally and not at Google scale: Dapper needed sampling because instrumentation overhead mattered at 10k+ requests/sec, and a 1/1024 sample sufficed [S11]; OTEP 235 exists to keep sampling decisions consistent across distributed tracers [S12]; SRE pre-aggregates on the server so consumers don't re-derive [S13]. **[REC]** PaperForge: deterministic full probes, no sampling. "One-pass" means each module is probed once per invocation and the aggregate is computed once within that invocation/response (then reused by the summary, detail and JSON renderers of that same response). Separate invocations — CLI, Agent, Obsidian — are independent; nothing is shared across invocations because there is no daemon. Per-probe timeouts are conditional: only where the local audit finds a blocking or remote probe. Sampling/shared-RNG/adjusted counts are **rejected** (ponytail: the machinery's only payoff is overhead reduction at scale; a single-process local CLI does not need it). If measured volume ever demands it, Dapper/OTEP describe the correct consistent-sampling machinery — deferred, evidence-gated, not a seam requirement.

**DA-4 — Per-module refresh/TTL, only where needed.** Two mature models. (a) Cheap validation before reuse: git `update-index --refresh` "checks to see if merges or updates are needed by checking stat() information" [S9]. (b) TTL with expiry + conditional refresh: pip checks for a "suitable response stored... which has not expired", then makes "a conditional request to refresh" on expiry [S16]; uv "respects HTTP caching headers" and offers `--refresh`/`--refresh-package` escape hatches plus versioned cache buckets (v12→v13 on format change) [S15]. Kleppmann: TTL means "you sometimes read stale data... such staleness is often unacceptable" [S18]. **[REC]** No blanket refresh protocol. Cached or externally sourced views: cheap validation (stat/hash) first, TTL only as a declared per-module fallback, always with an "as of" marker and an explicit `--refresh` escape hatch. Views recomputed from local authorities on each read need none of this [S9][S16][S15][S18].

**DA-5 — Partial failures.** Fowler's CircuitBreaker (popularized by *Release It!*): remote calls "can fail, or hang... cascading failures"; on failure, "some stale data that's good enough to display" is acceptable degradation [S19]; *Release It!* catalogs timeouts, bulkheads, fail-fast, graceful degradation, steady state [S20]. clig.dev: "Return zero exit code on success, non-zero on failure. Map the non-zero exit codes to the most important failure modes"; recoverability [S6]. Homebrew doctor is the local-CLI exemplar: warnings never abort; every check runs; "Will exit with a non-zero status if any potential problems are found"; clean run prints "Your system is ready to brew." [S23]. **[REC]** Per-module outcome enum (ok / stale / degraded / failed / skipped); the aggregate completes with annotated gaps; exit code reflects the worst failure tier; degraded modules fall back to marked-stale read models where one exists. Timeouts are conditional on the audit finding a blocking/remote probe — local deterministic probes need none. Server machinery (circuit-breaker thresholds, bulkhead pools) rejected — the local analog is outcome enums + tiered exit [S19][S23].

**DA-6 — Summary/detail query separation.** CQRS motivation is exactly this: different query shapes for different needs, per bounded context [S1]. clig.dev: "Human-readable output is paramount. Humans come first, machines second"; machine output is opt-in (`--json`, `--plain`); "By default, don't output information that's only understandable by the creators of the software" [S6]. git: `status` (summary) vs `diff`/`show` (detail) [S8]; hledger: `balance` (aggregate) vs `print` (full) [S10]. **[REC]** Per command: human summary (default) + opt-in machine detail (`--json`, versioned, additive — cross-ref CliProtocolResearch: pip installation-report `version` field, gh `--json` explicit field lists). No requirement that raw authorities be a client surface; optional per-module export/debug commands may expose them. Summaries come from the one-pass aggregation of that invocation (DA-3).

**DA-7 — Diagnostics separation.** Homebrew makes diagnostics a first-class *capability*, separate from commands: enumerated checks, each runnable individually (`--list-checks`, named check args), tiered findings, JSON output, exit semantics [S23]; "With `--verbose` or `--debug`, many commands print extra debugging information" [S25]. 12-factor: "Treat logs as event streams... each running process writes its event stream, unbuffered, to stdout" — the app never owns log routing/storage [S14]. SRE: keep monitoring as "distinct systems with clear, simple, loosely coupled points of integration"; drop signals nobody uses [S13]. clig.dev: `stderr` for messaging, `-d/--debug`, rewrite errors for humans [S6]. **[REC]** Diagnostics is one capability among others (PaperForge already has an architecture-audit surface — audit anchors only, no layout prescription): modules with real checks expose them; the control plane aggregates tiered findings and maps exit codes. Do **not** force a `diagnose()` method onto every module.

**DA-8 — CLI adapters.** Hexagonal: "Create your application to work without either a UI or a database so you can run automated regression-tests against the application..."; "The rule to obey is that code pertaining to the inside part should not leak into the outside part"; CLI/GUI/batch/test are adapters on ports [S4]. Clean Architecture: dependency rule; "The Web is a detail. The database is a detail." [S5]. Bernhardt's Boundaries/FCIS: simple values cross boundaries; imperative shell owns IO, functional core owns decisions [S21][S22]. **[REC]** Parse/render live in adapters — and the CLI command modules (the parse/arg layer) are part of the adapter, so they **may** import argparse/click; inner capability logic may not. The core never checks TTY or imports CLI/OS presentation libraries; Obsidian and Agent adapters call the same inner API. Adopt the boundary discipline; defer strict purity enforcement per-function (ponytail: enforce at the import/boundary layer).

**DA-9 — Avoiding pass-through service classes.** Fowler: services holding all logic over data bags "incur all of the costs of a domain model, without yielding any of the benefits"; Service Layer "is kept thin. It does not contain business rules... but only coordinates tasks and delegates" [S2][S3]. Ousterhout: modules should be deep — "simple interfaces for the common use cases, yet still provide significant functionality" [S17]. Kleppmann: write→read translation is a process with its own logic, not a facade [S18]. **[REC]** Every seam class must own at least one real concern (sequencing, aggregation, failure composition, refresh, exit mapping). If a class only forwards, delete it and let the caller talk to the module directly. This also applies to any proposed uniform interface: if a status/diagnose/read wrapper adds no behavior for a given module, it is a shallow module and must not be created.

## 3. Adopt / Defer / Reject

**Adopt** (smallest deep seam over existing modules)
- A.1 Authority-vs-read-model distinction per module; read models rebuildable [S8][S9][S18][S7].
- A.2 Thin control plane owning only orchestration per invocation: dispatch, deterministic full probe, one-pass aggregation within the response, partial-failure composition, tiered exit codes [S10][S23][S5][S6].
- A.3 Commands as thin intents; capability modules hold logic [S26][S5][S24].
- A.4 Three adapters (CLI/Obsidian/Agent) over one inner API; CLI command/parse modules may import argparse/click; inner capability logic may not [S4][S5][S21][S22].
- A.5 Summary-default output + opt-in versioned additive `--json` [S6]; output contracts additive and version-checked (CliProtocolResearch cross-ref).
- A.6 Partial-failure: per-module outcome enums, degrade-don't-abort, tiered exit [S19][S23][S6].
- A.7 Staleness honesty limited to where it applies: provenance/as_of/refresh only for cached or externally sourced views; cheap validation first; declared TTL + `--refresh` where needed [S9][S16][S15][S18].
- A.8 Diagnostics as a first-class capability where real checks exist (audit-style commands); tiered findings → exit code [S23][S13].
- A.9 Deep-module and dependency-rule discipline as the audit's review criteria [S17][S5].

**Defer** (adopt only if the local audit shows a concrete need; evidence-gated)
- D.1 Uniform status/refresh/diagnose protocol across all modules — adopt only per-module, per-need; never as a blanket interface (shallow-module risk) [S17].
- D.2 Per-probe timeouts — only where the local audit finds an actual blocking or remote probe [S19][S6].
- D.3 Per-module TTL — only for cached or externally sourced views where invalidation triggers are unavailable [S16][S15].
- D.4 Obsidian/Agent adapter parity — build the CLI adapter first; add others when a real consumer exists (YAGNI) [S4].
- D.5 Sampling/shared-RNG/adjusted counts — deferred behind a measured-volume gate; do not design for it now [S11][S12].
- D.6 Strict FCIS purity — adopt the boundary rule; defer per-function purity enforcement [S21][S22].
- D.7 Exposure of raw authorities (export/debug commands) — optional per-module, only if a consumer asks [S8].

**Reject**
- R.1 One aggregate control-plane god-module [S2][S3][S17][S24][S10][S8].
- R.2 Full CQRS / event sourcing / separate read processes / eventual-consistency machinery [S1].
- R.3 Single canonical store for everything (one DB/index) [S7][S8].
- R.4 Pass-through service/reporting facades; forced uniform interfaces [S2][S17].
- R.5 Sampling, shared RNG, adjusted counts for local deterministic probes; cross-invocation/cross-client aggregate sharing without a daemon [S10][S23] (contrast with server-scale need: [S11][S12]).
- R.6 Circuit-breaker thresholds, bulkhead pools, app-owned log files [S19][S14].
- R.7 Domain logic in command objects or inner capabilities' adapters [S26][S22].
- R.8 Catch-all subcommands / arbitrary abbreviations [S6].

## 5. Open risks and questions (for the grilling ticket)

- **Local audit dependency**: which artifacts are authorities vs derived is an empirical fact only the local audit can establish (e.g., is the vault the authority, or a read model over Zotero?). This report deliberately stops short of that mapping.
- **Windows/win32**: mtime/stat-based invalidation and atomic rebuilds differ on NTFS/case-insensitive filesystems — validate refresh triggers on the target platform if the audit adopts cached views.
- **No-daemon constraint**: aggregate reuse is per-invocation only; multi-consumer freshness (Obsidian Bases reading derived state) relies on each consumer invoking independently and on "as of" labels only where views are cached/external.
- **ProbeAll cost on large vaults**: deterministic full probes may be slow; mitigations are per-module cheap validation and incremental refresh of cached views — not sampling.
- **Exit-code taxonomy**: partial-failure exit codes need an explicit documented mapping before agents depend on them [S6].
- **Read-model stability**: since read models are the client surface, their schema/versioning matters more than authority internals; define versioning where a read model is consumed by Agent/Obsidian.
