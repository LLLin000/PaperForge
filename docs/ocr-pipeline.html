PaperForge OCR 当前流程

以仓库 master 为准：V3 流水线、派生重建、产物布局，以及 Phase B 只读版式计划的旁路位置。

执行阶段 权威产物 / 不变量 易错点（历史事故区） 只读旁路（Phase B）

1. 三条线：控制面、执行面、产物面

前端（Obsidian 插件 / CLI / Agent）不直接读写 OCR 产物。它们只发送 action，由 Python 侧的 action registry 校验能力与作用域后执行；每个模块对外返回状态信封，而不是各自解释内部状态。

2. 单篇论文的主流水线（V3 默认开启）

顺序不是风格问题：每一阶段都对上一阶段的写入做假设。下图把“阶段”和“它写下的文件/不变量”并排放，方便对照真实磁盘状态。

V3 的核心变化：匹配在角色硬提交之前运行。固定顺序是 raw → structured(seed) → pre_match → 匹配 → post_match → writeback → inventory → 对象提取 → 渲染。 在 555 篇真实语料上，V3 与旧顺序相比 547 篇无差异、5 篇更正确；这是“匹配看到证据、normalize 才提交”的直接证据。

4. 派生重建（rebuild）走哪条路

重建不重新识别字符：它从 canonical/blocks.raw.jsonl 出发，重新走结构化、匹配、归一化、归属与渲染。两个实现细节决定了它和首次解析是否“同一件事”。

阶段

  • phase 1：span 回填与 PDF 行证据（有 PDF 时）
  • phase 2：元数据富化 → structured(seed)
  • phase 3：图表匹配 → 写回角色 → post_match → 对象写回 → 库存落盘
  • 之后：渲染、健康、发布标记

实测结论

在 2AGGSMVQ、23T2B8ZX 上逐阶段对比：原始块、结构化、pre_match、图库存完全一致；唯一差异是重建在 phase 3 先做 write_back_figure_roles，生产链路在写回时才做同样提升——最终 blocks.structured.jsonl 逐块一致。

证据：docs/ocr-rebuild-equivalence.md

不要用“文件存在”判断完成。发布由 result hash + pending 标记控制：先写 pending，验证通过再清除。崩溃或失败留下的半成品会被标记拦住，而不是被下游当新结果消费。

5. Phase B：只读版式计划（当前旁路）

它在主流水线之外读取结构化块，输出区域树、阅读顺序和冲突，不写任何产物、不改 role。下图标出它站在哪里：

它在 40 篇复杂版式论文上的实测（587 页，10,430 块）

指标结果说明
块覆盖10,430 / 10,430缺失 0、重复 0；1,767 块是页眉页脚，单独计入
右→左跨栏跳跃OCR 287 处 / 计划 0 处计划按栏序读取，不再跨栏折返
与 OCR 相邻顺序一致94.1%（582 / 9,843 处不同）这只是“与 OCR 的一致率”，不是准确率；质量闸门另有人工核验
检测到的 OCR 跨栏冲突244 处计划认为这些位置 OCR 顺序跳栏
HOLD（无法判定）201 块严重度 hold；保留 OCR 位置，不进入高置信顺序
为什么 HOLD 重要：版面证据不足时强行排序，等于把不确定性变成错误。计划把这类块单独标出，留给后续阶段或人工，而不是“看起来完整”。

质量闸门还发现了两件事：① 阅读判定现在继承区域置信度——两栏各 2 块的弱分栏只能给出 0.50 置信，不允许包装成 0.70 的“跨栏交接”；② 页眉页脚只接受 noise/footnote 类角色，正文段落和小节标题即使落在页面 8% 带内也留在正文流里（此前有 2 个正文段落和 2 个小节标题被当成家具移到页尾）。

6. 不变量清单

不变量违反时的现象
匹配用候选角色（role_candidate → role → seed_role）图注先被 normalize 定成正文，匹配再也看不见它
writeback 早于 inventory 落盘图在、文字在、关联消失；重建一次才恢复
figure_inner_text 通过扩展裁剪框并入图片图下方多出一串坐标轴文字/变量名
发布依赖 result hash + pending 标记断电/中断后的半成品被当作完成结果
只读 action 不改变 vault 字节协议一致性测试会直接失败
版式计划不写 role、不写盘Phase B 就变成了又一套生产决策
